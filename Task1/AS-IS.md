AS-IS: анализ текущей архитектуры AdScale
1. Текущее состояние

AdScale представляет собой монолитное приложение на C++ / Go / Python / Node.js с одной PostgreSQL и одним production-кластером.

Текущая нагрузка — до 15 000 RPS. P95 времени отклика составляет 110–120 ms при требовании не более 100 ms. После подключения нового DSP нагрузка увеличится примерно до 18 000 RPS, при этом новый партнёр требует время ответа не более 80 ms.

Запаса по производительности у системы нет.

2. Основные проблемы
-  Общая PostgreSQL

Одна база данных используется для RTB, рекламных кампаний, статистики, финансов и аналитики.

Разные типы нагрузки конкурируют за CPU, I/O и подключения к БД. Нагрузка аналитики и статистики может увеличивать latency RTB.

Кроме того, одна PostgreSQL является единой точкой отказа.

- Синхронные обращения к БД в RTB

Ad Server и Auction Engine синхронно читают данные из PostgreSQL.

PostgreSQL находится в критическом пути аукциона, поэтому увеличение времени ответа БД напрямую увеличивает latency RTB.

- Отсутствие кеша

Данные кампаний, ставок и таргетинга читаются непосредственно из PostgreSQL.

Это создаёт большое количество повторных запросов и дополнительную нагрузку на БД.

- Прямая запись статистики

Statistics Service записывает impressions и clicks напрямую в PostgreSQL.

Буферизация и очередь отсутствуют. При росте RTB-трафика одновременно растёт write-нагрузка на общую БД.

- Аналитика в production-БД

Analytics Service выполняет тяжёлые SQL-запросы непосредственно в PostgreSQL.

Read replica или отдельного аналитического хранилища нет, поэтому аналитика конкурирует за ресурсы с RTB и другими операциями.

- Монолитное приложение

Компоненты имеют разные профили нагрузки, но не могут масштабироваться независимо.

В частности, Auction Engine нельзя масштабировать отдельно от остальных компонентов.

- Отсутствие асинхронной обработки

Брокер сообщений отсутствует.

Потоки impressions и clicks нельзя отделить от основной нагрузки и сгладить их пики.

- Инфраструктурные ограничения

Deployment выполняется вручную.

Контейнеризация отсутствует.

Используется один production-кластер.

Это затрудняет горизонтальное масштабирование и увеличивает риск downtime при изменениях.

3. Влияние на latency

Основная цепочка проблемы выглядит так:

- Рост bid requests

- рост количества обращений к PostgreSQL

- рост количества impressions и clicks

- увеличение write-нагрузки

- конкуренция за ресурсы PostgreSQL

- рост времени ответа Auction Engine

- рост P95

- таймауты и проигранные аукционы.

При текущих 15 000 RPS требование по latency уже нарушается, поэтому увеличение нагрузки до 18 000 RPS без архитектурных изменений создаёт высокий риск дальнейшей деградации.

4. Основные риски
Превышение SLA нового DSP.
PostgreSQL становится bottleneck при росте нагрузки.
Отказ PostgreSQL влияет на большую часть системы.
Статистика и аналитика ухудшают RTB latency.
Невозможно независимо масштабировать Auction Engine.
Ручной deployment повышает риск downtime.
Один production-кластер не обеспечивает требуемую отказоустойчивость.
5. Вывод

Основные ограничения текущей архитектуры:

Общая PostgreSQL находится в критическом RTB-пути.
Критичная и некритичная нагрузка не изолирована.
Отсутствуют кеширование и асинхронная обработка событий.
Компоненты нельзя масштабировать независимо.
PostgreSQL и production-кластер являются точками отказа.

Для дальнейшего масштабирования необходимо постепенно отделить RTB-контур от остальных нагрузок и обеспечить независимое масштабирование его критичных компонентов.
